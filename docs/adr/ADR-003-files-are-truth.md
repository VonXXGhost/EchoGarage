# ADR-003：文件即真相——标签、封面与元数据缓存

- 状态：已批准（Accepted，2026-11-09，owner；2026-11-21 补充封面缓存上限；2026-11-25 增补未落盘手动 BPM 状态说明）
- 日期：2026-11-09

## 背景

用户明确要求：Tag 必须是封入歌曲文件的标准 Tag，而不是播放器额外记忆的数据；界面又要尽可能快。

## 决策

1. **文件是唯一真相**：标题、艺术家、专辑、时长、比特率、采样率、封面等全部从文件读取。
2. SQLite 的 `tracks` 表是**可重建的缓存**；除软件自身状态（`PlayCount`、`LastPlayedAtUtc`、`Rating`）外，
   所有字段都能从文件重新推导。
   - 2026-11-25 补充（ADR-034）：独立表 `track_bpm_cache` 中的**自动测量 BPM（`MeasuredBpm`）** 属于可重算的
     派生分析缓存（同 ADR-015 波形缓存），可在设置页「清空缓存」中单独清理；用户手动修正但选择**不写入文件级 Tag**
     的 **`ManualBpm`** 登记为软件侧用户状态（与 `Rating` 同级），随 `library.db` 持久保留、不随「清空缓存」删除；
     勾选写入音频文件标签后即落盘并清空 `ManualBpm`，回归「文件即真相」。
3. 写入标签时通过 TagLib# 直接修改文件：
   - `.mp3` → ID3v2
   - `.flac` → Xiph / Vorbis Comment
   - `.m4a/.mp4` → Apple (iTunes) 标签
   - `.wav/.aiff` → RIFF 内嵌 ID3v2
   - 文件原本没有标签块时，用 `File.GetTag(type, create: true)` 创建。
4. 封面：优先读取文件内嵌封面（FrontCover 优先），没有时回退到同目录的封面图片（cover/folder/front/album…）；
   解码后按“专辑身份”缓存到磁盘。
5. 缓存键（`CoverKeyFactory`）：
   - 有专辑：`album_<hash>`，其中 `hash = sha1("album|" + albumArtist.Trim().ToUpperInvariant()
     + "|" + album.Trim().ToUpperInvariant())` 的十六进制前 20 位（小写）；
   - 无专辑：`file_<hash>`，其中 `hash = sha1(path.Trim().ToUpperInvariant())`，同样截断到前 20 位。
6. 封面未找到时写入 `<key>.none` 标记，内容为源文件的 `mtime:size`；源文件变化后标记失效，不会重复解析。
   - **按文件**的封面键（无专辑）：用 `<key>.stamp` 严格校验，文件变化后自动重建缓存。
   - **按专辑**的封面键：同一专辑的多首歌共享封面，不能用某一首歌的 `mtime` 判定失效（否则会反复删/建）；
     专辑封面一旦提取成功就保持稳定，只有显式 `Invalidate`（软件内改标签）或清空缓存才重建；
     未命中时仍按当前请求文件的 stamp 判断，允许“先请求到无封面的歌、后请求到有封面的歌”时补抓。
7. 修改标签后的刷新链：写文件 → 重新索引该文件 → 失效旧/新封面磁盘与内存缓存 → 刷新行、正在播放面板与计数。

### 封面缓存的容量上限（2026-11-21 补充）

1. **内存**：`CoverImageService.MemoryCacheByteLimit = 1024 MB`（owner 指定的硬上限）+ 条目数护栏
   `MemoryCacheEntryLimit = 512`；容量记账抽成纯逻辑类 `CoverCacheBudget`（`Add` / `Touch` / `Trim`，
   始终保留至少一条），字节数按 `((PixelWidth × BitsPerPixel + 7) / 8) × PixelHeight + 96` 估算
   ——WPF 的像素缓冲在原生内存，GC 堆度量不到，必须手工记账。
2. **磁盘**：`FileCoverCache.LimitMb` 默认 **2048 MB**（0 = 不限制），启动预热时按最后写入时间删到上限的
   90%，并连带删除同名 `.stamp` / `.none` 伴生文件；设置页「封面缓存上限」可选
   256 / 512 / 1024 / 2048（默认）/ 4096 / 不限制。
3. **解码尺寸随 DPI**（细节见 KB-008 §4.5）：列表行 24 DIP、分组封面 `groupCoverSize` DIP，
   解码宽度 = 显示尺寸 × `DpiScale`（行夹 32–256 px、分组 64–640 px），不再固定 128 / 512 px。
4. **可观测**：列表切换与可见分组封面裁剪时写 `Cover memory (...)`，磁盘裁剪写
   `封面缓存已按上限裁剪 files=… limitMb=…`。

实测（4K / 150%、4000 行分组列表、1604 个专辑组）：滚动 40 秒工作集 3,011 MB → 341 MB；
20 次 UIA 滚动 1,773.6 MB → 335.9 MB；把副本上限压到 8 MB 时磁盘缓存 431.5 MB → 7.0 MB。
缓存仍是纯派生物，删除后按需重建，决策 1–7 不变。

## 理由

- 满足“标签属于文件”的核心诉求，换播放器后标签不丢。
- 专辑级封面缓存避免同一专辑 15 首歌重复解析 15 次。
- 负缓存避免对没有封面的文件反复打开（在数千首库里非常明显）。

## 后果

- 标签写入失败时（只读文件、格式不支持）必须在 UI 上明确报错，不能悄悄只改数据库。
- 外部工具修改标签后，需要靠扫描 / 文件监听重新索引才能反映到界面；播放列表中的外部文件另由
  ADR-018 在窗口激活 / 切换来源时后台刷新。
- 时长以文件为准；数据库中的时长只是扫描时的快照。

## 备选方案

- 把标签存进数据库、文件只读：违背需求，且换软件即丢失。
- 每次显示都实时读文件：启动与大列表会明显变慢。
