# ADR-007：文件监听与缓存失效

- 状态：已批准（Accepted，2026-11-09，owner）
- 日期：2026-11-09

## 背景

媒体库目录会变化（下载、移动、重新打标签），用户希望界面“总是显示文件最新状态”，同时不能因为监听事件风暴卡住 UI。

## 决策

1. 每个媒体库文件夹一个 `FileSystemWatcher`：
   - `IncludeSubdirectories = true`
   - `NotifyFilter = FileName | DirectoryName | LastWrite | Size`
   - `InternalBufferSize = 64 KB`
   - 忽略 `ReparsePoint` 目录，避免软链接环路。
2. 事件只上报“路径 + 变化类型”；**去抖 900ms** 后在 UI 线程批量处理：
   - 文件存在 → 重新索引该文件，并刷新来源与当前列表；
   - 文件不存在 → `IsMissing = 1`。
3. 增量判断始终基于 `FileSize + LastWriteTimeUtc`；监听事件只是“提示可能有变化”，最终以文件系统状态为准。
4. 启动扫描与监听互补：监听保证运行期实时性，启动扫描补齐离线期间的变化。
5. 封面缓存同样依赖 `mtime:size` 作为失效依据；文件变化后旧缓存不再被引用。

## 理由

- 批量 + 去抖避免复制一个专辑时触发上百次重载。
- 以文件系统状态为准可以容忍事件丢失、重命名顺序错乱、编辑器“先写临时文件再替换”等行为。
- 监听只做索引更新，不递归全库扫描，操作代价与变化文件数成正比。

## 后果

- 极端情况下（监听缓冲区溢出）会漏掉部分事件，启动扫描或手动 F5 可补齐；溢出会写日志。
- 网络驱动器上的 `FileSystemWatcher` 语义较弱，建议把媒体库放在本地磁盘。

## 备选方案

- 定时全库轮询：CPU / 磁盘开销更大，且“变化后要等一个周期”。
- 只靠手动刷新：不满足“自动跟踪变化”。
